# abslab — Claude Code guidance

## Git policy

**NEVER run `git add`, `git commit`, or `git push`** — the user manages all git
operations themselves. Do not stage, commit, or push anything under any
circumstances, even if asked mid-task; instead make the file changes and let the
user handle git. Read-only git commands (`git status`, `git diff`, `git log`) are fine.

## Project overview

NixOS configuration using **flake-parts** + **import-tree** with the **dendritic module pattern**.
All `.nix` files under `modules/` are auto-loaded by `import-tree ./modules` — no manual import list to maintain.

Hosts: `lazarus` (desktop, inherits `pc`), `halflight` (laptop, inherits `laptop → pc`).
Owner username: `absentia`. Home directory: `/home/absentia`.

Compositor: **Hyprland** with the scrolling layout, started by **uwsm** (NixOS `programs.hyprland.withUWSM`). Every session, at boot and after a logout, starts at **Noctalia Greeter** on greetd (nixpkgs `services.displayManager.noctalia-greeter`, `login/greeter.nix`), which asks for password + YubiKey touch and launches `uwsm start hyprland-uwsm.desktop`; Noctalia auto-syncs its appearance (passwordless polkit rule). There is deliberately no autologin: the password unlocks the GNOME keyring (`login` keyring, with the login password) through PAM, which autologin can't. niri was replaced to match the Arch setup — don't reintroduce it. Config is **Lua**, generated by HM (`wayland.windowManager.hyprland`, `configType = "lua"`; package/portal come from the NixOS module, uwsm owns the session target):
- **Data** goes in `settings` (`config` → `hl.config`, plus `monitor`, `workspace_rule`, `window_rule`, `layer_rule`, `device` lists) — merges across modules, overridable by hosts.
- **Behaviour** (binds, event handlers) goes in `extraConfig` as Lua lines, spread across feature modules (dendritic style), e.g. `bind(mod .. " + D", cmd(ipc .. "panel-toggle launcher"), "App launcher")`. Helpers are Lua locals from `settings` (`_var`): `mod`, `bind(keys, action, desc, opts)`, `app` (runs via `uwsm-app`), `cmd` in `window-manager/hyprland/enable.nix`; `ipc` (`noctalia msg `) in `noctalia.nix`. Every bind needs a description (`Mod+Shift+/` lists them).
- Compositor-level config lives in `modules/window-manager/hyprland/`; per-host monitors/keyboards in `hosts/<name>/`.
- **Verify** a generated config before handing it over: build `…home-manager.users.absentia.xdg.configFile."hypr/hyprland.lua".source` and run `Hyprland --verify-config -c <copy>` — it catches unknown keys and bad dispatchers.
- Border colours come from the Rosé Pine palette (see Theming).

Desktop shell: **Noctalia v5** (HM `programs.noctalia`, systemd user service) — bar, launcher, notifications, lock screen, idle, wallpaper, clipboard history, OSD, screenshots and the polkit agent. Its TOML settings (`programs.noctalia.settings`) are spread across feature modules like the binds (core in `window-manager/noctalia.nix`, bar in `bar.nix`, idle/lock/wallpaper/notifications in their own files) and validated at build time; binds call `noctalia msg …`. The lock screen authenticates against the `login` PAM service (YubiKey rules in `security/yubikey.nix`). **YubiKey policy: the touch is for logins only** (`login`, which TTY, lock screen and greetd use); U2F is not enabled globally, so sudo, su, run0, polkit, passwd etc. stay password-only. The configuration mirrors the Arch setup in `~/projects/arch` (absrice `noctalia/config.toml.tmpl`). **Prefer Noctalia over any program whose job it can do** — menus use `noctalia dmenu` (scripts) or launcher entries under `shell.launcher.dmenu.entry.<id>` (e.g. the `/run` menu in `desktop/launcher.nix`). rofi is gone: Bitwarden (`Mod+M`, `bitwarden/menu.nix`) is a two-step `noctalia dmenu` menu over rbw that only ever *types* secrets with `wtype` (stdin, never argv) — **no secret may go to the clipboard** (Noctalia keeps clipboard history); rbw unlocks via `pinentry-gnome3`; rofimoji (`Mod+U`, emoji + all Unicode) runs behind a `dmenu` shim that shows it in Noctalia's launcher (`desktop/character-picker.nix`).

## Module system

### Namespaces

| Attribute | Purpose |
|---|---|
| `flake.modules.nixos.<key>` | NixOS module |
| `flake.modules.homeManager.<key>` | Home Manager module |
| `flake.meta.*` | Project-wide metadata (owner, fonts, etc.) |
| `configurations.nixos.<hostname>.module` | Host entry point |

### How HM is wired

`modules/home-manager/nixos.nix` wires HM into NixOS modules:
- `base` NixOS module → loads `homeManager.base` and `homeManager.lazyvim` for all users
- `pc` NixOS module → loads `homeManager.gui`
- `laptop` NixOS module → loads `homeManager.laptop`

To add a new HM module to all desktop hosts, add it to `pc` in that file (or create a new NixOS module key and import it in host imports).

`modules/home-manager/checks.nix` also builds `base`/`gui`/`laptop` as standalone HM
flake checks (no host), using an `osConfig` stub. When an HM module
reads a new `osConfig.<path>`, add that path to `osConfigStub` there — otherwise the
checks fail with `expected a set but found null`. Optional reads that should
fall back when there is no host use `osConfig ? null` and must stay absent from the stub.

### Module keys

Keys are simple attribute names — not slash-delimited strings:

```nix
flake.modules.nixos.myFeature = { pkgs, ... }: { ... };
flake.modules.homeManager.myFeature = hmArgs: { ... };
```

### Referencing other modules

Always route through the tree — never use relative `../` imports:

```nix
{ config, ... }: {
  flake.modules.nixos.myFeature = {
    imports = [ config.flake.modules.nixos.otherFeature ];
  };
}
```

### Reading metadata

```nix
{ config, ... }: {
  flake.modules.nixos.myFeature = {
    fonts.fontconfig.defaultFonts.monospace = [ config.flake.meta.fonts.monospace.name ];
  };
}
```

### Host registration

```nix
# modules/hosts/<name>/imports.nix
{ config, ... }: {
  configurations.nixos.<name>.module = {
    imports = with config.flake.modules.nixos; [ efi pc ];
  };
}
```

## Dendritic module rules

These rules are defined in `modules/docs/module-authoring.md` — read it for examples.

1. **Import to enable** — no top-level `enable` options. Importing a module activates it with good defaults.
2. **Co-locate NixOS + HM** — when a feature spans both layers, put both `flake.modules.nixos.x` and `flake.modules.homeManager.x` in the same file.
3. **`lib.mkDefault` on all values** — so hosts can override without `lib.mkForce`.
4. **Options namespace** — use `options.services.<name>` for nixpkgs-style services; use `options.flake.meta.*` for project-wide data; avoid inventing new top-level namespaces unless necessary.
5. **Scripts** — inline if ~20 lines or fewer; otherwise put in a sibling `scripts/` directory and load with `pkgs.writeShellApplication` or `builtins.readFile`.
6. **No `enable` guards** — never wrap `config = lib.mkIf cfg.enable { ... }` as the primary activation pattern.

## Installing tools

Pick the first that exists — verify by evaluating the option, don't assume:

1. Home Manager module (`programs.<x>.enable`, or `programs.gh.extensions` for gh extensions)
2. NixOS module (`programs.<x>`)
3. Plain package (`home.packages` / `environment.systemPackages`)

Exception: tools needing capabilities/setuid/groups (packet capture etc.) go through their
NixOS module even if HM could install the binary — HM can't grant privileges (e.g. `programs.wireshark.package = pkgs.wireshark`, `programs.bandwhich`).

Editor tooling for a language lives in `programs.lazyvim.extraPackages` in
`modules/dev/languages/<lang>.nix`, and matches what the LazyVim extra actually calls
(nix: `nil`, `statix`, `nixfmt` — same tools as `just lint` / `just fmt`).

## Impermanence

Both hosts wipe `/` on boot. A feature that keeps state under `/var/lib` persists it from
its own file, contributing to the `impermanence` NixOS module:
`flake.modules.nixos.impermanence.environment.persistence."/persist".directories = [ "/var/lib/docker" ];`
(as `virtualization/docker.nix`, `libvirt.nix`, `desktop/bluetooth.nix`, `networking/manager.nix`,
`login/greeter.nix` do). `modules/storage/impermanence.nix` lists only system-wide state.

## Directory conventions

```
modules/
  style/        ← visual theming (fonts live here; new theme modules go here)
  window-manager/ ← compositor, Noctalia shell (bar, idle, lock, wallpaper), etc.
  hosts/<name>/ ← per-host files (imports, monitors, hardware, etc.)
  home-manager/ ← HM wiring into NixOS
  docs/         ← authoritative pattern docs (read-only reference)
```

## Theming

One theme, **Rosé Pine** (main), dark only: no light mode, no switching, nothing rendered at runtime. Every program uses **Rosé Pine's own port** (rosepinetheme.com / github.com/rose-pine) where one exists, wired the program's native way; the ports nixpkgs lacks are `flake = false` inputs (`rose-pine-*` in `flake.nix`, updated with `nix flake update`). Stylix, Noctalia templates and the old variant/`theme-switch` machinery were removed — don't reintroduce them.

- **Ports**: kitty (`programs.kitty.themeFile`, from kitty-themes), Neovim (`vimPlugins.rose-pine`, loaded from the store with `dir` in `dev/lazyvim/colorscheme.nix`), btop, bat (also Codex's `codex/themes/rose-pine.tmTheme`, selected once with `[tui] theme = "rose-pine"` in Codex's own config.toml), yazi (flavor), eza, fzf (its colours copied into `programs.fzf.colors`), GTK (GTK 3 theme dir and GTK 4 stylesheet from `rose-pine/gtk`; GTK 3 keeps the default light preference, as the port asks, while dconf `color-scheme` is `prefer-dark` for libadwaita, Firefox and Obsidian), Qt via Kvantum (`rose-pine-iris`, linked into `Kvantum/` by hand since nixpkgs' package nests it one level deeper; qtct for fonts), the cursor (`rose-pine-cursor`), Noctalia (its builtin `Rosé Pine`), Firefox (the port's userChrome form: its `dist/` files in the profile's `chrome/`, `userChrome.css` followed by our tab-bar hiding, in `web-browsers/firefox.nix`).
- **No port**: the few settings that take a colour read **`flake.meta.rosePine`** (`style/rose-pine.nix`, rose-pine/neovim's palette): Hyprland borders (iris focused, muted otherwise, as the Hyprland port's example), zathura, imv's background, the bar's status colours (foam/gold/love = success/warning/error, as the GTK port maps them). Claude Code uses its built-in dark theme; Obsidian gets Rosé Pine's community theme in its own theme browser (kept in the vault).
- **`modules/style/fonts.nix`** sets the font families (`flake.meta.fonts`) and the fontconfig fallback chain (Symbols NF Mono → DejaVu Sans Mono → Noto Color Emoji) so kitty/etc. render dingbats/arrows/emoji — do **not** reintroduce a kitty `symbol_map`.
- **`modules/style/cursor.nix`**: Rosé Pine's cursor (`rose-pine-cursor`, `BreezeX-RosePine-Linux`); the greeter gets it too (`cursorTheme` in `login/greeter.nix`), since the appearance sync doesn't carry the cursor. That sync (`greeter_sync.auto_sync`) follows appearance changes made at runtime, not a new config at startup: after changing Noctalia's palette in Nix, run `noctalia msg greeter-sync` once.
- **`modules/window-manager/wallpaper.nix`** points Noctalia's wallpaper panel (`Mod+B`) at `~/pictures/wallpapers`; Noctalia also draws the lock-screen background.
- **State-coloured bar indicators** (battery, network, VPN, Bluetooth, camera) come from our own Noctalia plugin `absentia/status` (`window-manager/plugins/status/`, loaded as a read-only `path` source from the store). It works like Waybar's custom modules: each widget instance (`type = "absentia/status:exec"`) runs an `exec` script printing `{ glyph, text, tooltip, class }` JSON, re-run on each line of a `watch` command and/or every `interval` seconds; `colors` maps class → a hex value or a Noctalia colour role, and `blink` lists flashing classes. Scripts live next to the widget (`bar-status.nix`, VPN in `networking/vpn-menu.nix`). Check plugin changes with `noctalia plugins lint <dir>`.
- **Spotify and Discord are the official clients** (`desktop/apps/spotify.nix`, `discord.nix`), deliberately unthemed: alternative clients (Spotifast, Vesktop) were tried for theming and dropped as too much upkeep. Discord's camera opens `/dev/video*` directly, which Noctalia's PipeWire-based privacy widget can't see; the bar's camera widget (`bar-status.nix`) covers it.

## Misc

- Pipe operator `|>` is enabled globally via `nixConfig.extra-experimental-features`.
- **Dev shell** is make-shell under `perSystem` (`make-shells.default` in `modules/just.nix` + `security/sops.nix`), loaded by direnv via `.envrc` → `use flake`. devenv was removed — don't reintroduce it. The shellHook's `exec zsh` is skipped under direnv (`DIRENV_IN_ENVRC`); known limitation: `nix develop -c <cmd>` hangs in an interactive zsh (accepted).
- **`hosts/*/hardware-configuration.nix`** keeps `nixos-generate-config`'s shape (easy to regenerate/diff), so don't restyle it; `just lint` skips it for statix.
- **Evaluating changes**: flakes ignore untracked files, so test with `nix eval "path:$PWD#nixosConfigurations.<host>.config.system.build.toplevel.drvPath"` until the user has `git add`ed new files.- `flake-parts` modules system: see `modules/flake-parts.nix` and `modules/configurations/nixos.nix`.
- `modules/docs/dendritic-core.md` and `modules/docs/module-authoring.md` are the canonical pattern references — read them before authoring new modules.
